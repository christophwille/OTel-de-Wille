# LamplightCsharp — executable telemetry contracts for an Aspire app

An [Aspire](https://aspire.dev) 13 (.NET 10) sample whose *instrumentation* is the thing under test.
[Lamplight](https://github.com/rockingsoft/lamplight) (a rewrite of Tracetest, MIT) fires an HTTP request that
carries its own W3C `traceparent`, then asserts on the **spans** and **PromQL metrics** its embedded OTLP receiver
sees for that trace. The tests live in `lamplight/*.wick` (HCL) and read like a contract:

- the order workflow crosses a service boundary and the trace context must survive the hop;
- the domain span `create order` must exist exactly once with the right `order.status`;
- the business counter `orders.created` must move by exactly one;
- a business rejection (out of stock) is a `409` with a non-error span, not an exception.

Projects:

- **Orders.Api** — `POST /orders` reserves stock via `http://inventory` (Aspire service discovery), stores the order
  in memory, emits the `create order` span (`order.sku`, `order.quantity`, `order.status`) and the
  `orders.created` / `orders.rejected` counters. `GET /orders/{id}` reads it back.
- **Inventory.Api** — `POST /inventory/{sku}/reserve` against an in-memory stock list (`WIDGET-1` = 100,
  `GADGET-7` = 0), emits the `reserve stock` span (`inventory.sku`, `inventory.result`).
- **LamplightCsharp.ServiceDefaults** — the Aspire template plus dual OTLP export (see below).
- **LamplightCsharp.AppHost** — wires both services and sets `LAMPLIGHT_OTLP_ENDPOINT` on them.

## Prerequisites

- .NET 10 SDK and the Aspire CLI (`aspire --version` ≥ 13.5)
- Lamplight ≥ 0.7.0: download `lamplight_<version>_windows_x86_64.zip` from the
  [releases](https://github.com/rockingsoft/lamplight/releases), put `lamplight.exe` on `PATH`
  (this sample was built with it in `%USERPROFILE%\.local\bin`). macOS/Linux: `curl -fsSL https://raw.githubusercontent.com/rockingsoft/lamplight/main/install.sh | sh`.
- No container runtime needed.

## Run

Terminal 1, start the app and keep it running:

```powershell
aspire run
# or: dotnet run --project LamplightCsharp.AppHost --launch-profile http
```

Terminal 2, run the contracts (Lamplight does not start the app; it expects it at `BASE_URL`, default `http://localhost:5180`):

```powershell
lamplight validate
lamplight list tests
lamplight run                         # all three tests, ~10 s
lamplight run --tag smoke             # healthcheck + create_order
lamplight run --json-file result.json --keep-artifacts
lamplight run reject_order_out_of_stock --var BASE_URL=http://localhost:5181   # wrong service -> exit code 1
```

Exit codes are stable: `0` all checks passed, `2` a check failed, `1` a technical error (the wrong-service example
above is a `1`: the 404 from the inventory service has no content type, so the contract's JSON expressions cannot be
evaluated at all). Failed runs keep their artifacts (`result.json`, `checks.json`, …) under `%TEMP%\lamplight-run-*`.

Open the dashboard URL printed by the AppHost to see the same trace (`orders` → `inventory`) and the
`orders.created` metric that Lamplight just asserted on.

## What each test proves

`lamplight/orders.wick`

| Test | Trigger | Evidence |
| --- | --- | --- |
| `create_order` | `POST /orders` `WIDGET-1` ×2, then `GET /orders/{id}` from the step output | 201; exactly one `create order` span in service `orders` with `order.status == "created"` and no error; exactly one `reserve stock` span in service `inventory` with `inventory.result == "reserved"` (trace context survived the hop); exactly one auto-instrumented `client` span with `http.response.status_code == 200`; `orders_created_total` delta == 1 |
| `reject_order_out_of_stock` | `POST /orders` `GADGET-7` | 409; `create order` span with `order.status == "rejected"` and *not* marked error; `reserve stock` span with `inventory.result == "insufficient"`; `orders_rejected_total` delta == 1 |
| `healthcheck` | `GET /health` | 200 (generated by `lamplight init`; `/health` is excluded from tracing by ServiceDefaults) |

Each test owns its own counter, so Lamplight's default four parallel workers cannot disturb each other's metric delta.

## MCP: let the agent drive Lamplight

`.mcp.json` registers Lamplight's stdio MCP server for Claude Code at project scope (`claude mcp add --scope project lamplight -- lamplight mcp --working-dir .`).
Start `claude` in this directory, approve the server once, then try:

> Run the smoke tests and use the failed telemetry contract to identify which layer I should investigate.

> Compare the `create_order` contract with a fresh trace and tell me whether instrumentation still emits the required spans and attributes.

> Add a regression test that proves a `GET /orders/{id}` for an unknown id returns 404 and emits no `create order` span.

The server exposes `lamplight_list_tests`, `lamplight_scaffold_test`, `lamplight_validate_test_content`,
`lamplight_write_test_file` (hash-protected), `lamplight_observe_trace`, `lamplight_run_tests` and friends.
The repository also ships agent skills (`npx skills add rockingsoft/lamplight --skill lamplight-trace-tests opentelemetry-instrumentation --agent claude-code`).

## How the telemetry gets to Lamplight (Windows notes)

- Lamplight's zero-code OBI instrumentation (eBPF) is Linux-only, so this sample uses the OpenTelemetry SDK that
  Aspire's ServiceDefaults already configures. Lamplight's receiver is OTLP/**HTTP** only (`http://127.0.0.1:4318/v1/traces`
  and `/v1/metrics`); port 4318 must be free while a run is in progress.
- `ServiceDefaults/Extensions.cs` exports to **two** destinations: the Aspire dashboard (env-configured, gRPC) and
  Lamplight (`LAMPLIGHT_OTLP_ENDPOINT`, set by the AppHost). The template's `UseOtlpExporter()` cannot coexist with
  per-signal `AddOtlpExporter()`, so both destinations are registered per signal with distinct option names.
- The Lamplight metric reader uses **delta** temporality. Lamplight starts a fresh receiver per run and sums delta
  points, so `metric.delta == 1` is stable run after run; a cumulative counter would report the process-lifetime total.
  Increments made while no receiver is listening (e.g. a manual `curl` right before a run) can be retried by the
  exporter into the next run and show up as `delta == 2`; let the services idle a moment or restart them.
- Lamplight translates OTLP metric names to Prometheus names: `orders.created` becomes `orders_created_total`,
  resource attributes become `resource_service_name`-style labels.
- `exactly = N` span checks wait for the whole `observation_window` because a push receiver cannot prove the trace is
  complete; `.lamplight` sets it to 10 s (Aspire flushes spans every second in development).

## Where to go next

Swap the `otlp` datasource for Tempo/Jaeger to assert against a real backend, add a `docker_compose` or `kubernetes`
target to run the contracts in CI, or add a k6 trigger for load-shaped contracts. See the Lamplight
[reference](https://github.com/rockingsoft/lamplight/blob/main/docs/reference.md).
